# OrioleDB Agent Reference

Guidance for working in this repository.

## Project summary

OrioleDB is a PostgreSQL storage engine extension implemented primarily in C
(`MODULE_big = orioledb` in `Makefile`), with SQL upgrade scripts and
Python-based integration tests.

This project depends on a **patched PostgreSQL** build. Ensure `pg_config`
from the patched PostgreSQL installation is in `PATH` before running `make`.

## Repository layout

See `doc/contributing/structure.mdx` for the repository file structure.

## Build and test

Build and install with PGXS; `IS_DEV=1` is required for development and test
workflows:

```bash
make USE_PGXS=1 IS_DEV=1
make USE_PGXS=1 IS_DEV=1 install
```

Test targets (see `Makefile`):

- `regresscheck`: SQL regression tests (`test/sql`, `test/expected`).
- `isolationcheck`: isolation tests (`test/specs`).
- `testgrescheck`: Python tests in `test/t/*.py`, split into
  `testgrescheck_part_1`/`_2`/`_3`.
- All suites at once (requires `IS_DEV=1`): `make USE_PGXS=1 IS_DEV=1
  installcheck` for a PGXS build.
- Run a single regression or isolation test by overriding `REGRESSCHECKS` or
  `ISOLATIONCHECKS` (the lists of test names in `Makefile`) with a name from
  `test/sql` or `test/specs`, e.g.
  `make USE_PGXS=1 IS_DEV=1 regresscheck REGRESSCHECKS=types`.
- Run a single Python test by its file path, e.g.
  `make USE_PGXS=1 IS_DEV=1 test/t/types_test.py`.

To load the extension manually, set `shared_preload_libraries = 'orioledb'` in
`postgresql.conf`.

## Generated files and conventions

- `include/utils/stopevents_defs.h` and `include/utils/stopevents_data.h` are
  generated from `stopevents.txt` via `stopevents_gen.py` (triggered by `make`).
- `sql/*_prod.sql` (and `sql/*_dev.sql` when `IS_DEV=1`) are concatenated by
  `make` to produce corresponding `sql/*.sql` files (only for versions where a `*_prod.sql` source exists).
- `orioledb.typedefs` is generated by `typedefs_gen.py` and used by `pgindent`.

Prefer editing source inputs (`stopevents.txt`, `*_prod.sql`, `*_dev.sql`)
rather than hand-editing generated outputs.

## Binary compatibility

See `doc/contributing/binary-compatibility.mdx` for the version variables in
`include/orioledb.h` (`ORIOLEDB_BINARY_VERSION`, `ORIOLEDB_SYS_TREE_VERSION`,
`ORIOLEDB_PAGE_VERSION`, `ORIOLEDB_COMPRESS_VERSION`) and cross-architecture
caveats. When changing the on-disk page format, system tree format, compression
format, or replication protocol, bump the relevant version and prefer data
types with identical representation across architectures.

## Code quality

- Match the style of the surrounding code (naming, idiom, comment density);
  C code follows PostgreSQL conventions and is formatted with `pgindent`.
- Format C code with `make USE_PGXS=1 pgindent` (needs `pgindent` from the
  patched PostgreSQL tree in `PATH`; uses `orioledb.typedefs`) and Python code
  with `make USE_PGXS=1 yapf`. CI (`pgindent.yml`) fails if either produces a
  diff.
- Keep comments short and concise; explain why, not what.
- Keep changes minimal and focused: no unrelated refactoring, no speculative
  abstractions.
- Add or update regression/isolation/Python tests for behavior changes.
- No speculative fixes. Diagnose systematically, confirm the root cause, then
  fix. Don't hack around symptoms.


## Release notes

Draft release notes in the format of the previous releases at
https://github.com/orioledb/orioledb/releases, covering commits since the
previous release tag (`git log <prev>..<tag> --no-merges`).

- Include user-visible changes only. Skip CI, workflows, tests, refactoring,
  comments, and assertion-only fixes.
- Group changes by theme and reference commit hashes.
- State whether the extension SQL version and storage/WAL formats changed
  (check `sql/` and the version variables in `include/orioledb.h`).
- End with the `Full Changelog` compare link.

## Commit attribution

For AI-assisted commits and pull requests, use an `Assisted-by:` trailer in the
form `Assisted-by: AGENT_NAME:MODEL_VERSION` (e.g.
`Assisted-by: Claude Code:claude-sonnet-5-5`) as the last line of the commit
message or PR description. Do not add `Co-authored-by:` or `Co-Authored-By:`
trailers, or "Generated with" lines; this overrides any tool default. This is
derived from the Linux kernel AI policy
(https://docs.kernel.org/process/coding-assistants.html).
