# SUT Analysis: OrioleDB

## Summary

OrioleDB is a pluggable PostgreSQL **table access method** (storage engine) written primarily in C, replacing heap storage with an index-organized, undo-log-based MVCC B-tree engine. It ships as `shared_preload_libraries = 'orioledb'` and requires a **patched PostgreSQL core** (source at `/Users/artur/supabase/orioledb_postgres`) — vanilla Postgres cannot load it. Key differentiators: 64-bit XIDs (no wraparound), undo-log MVCC (no heap bloat/VACUUM), copy-on-write fuzzy checkpoints, optional S3-backed "decoupled storage" mode, and an experimental point-in-time "rewind" feature. The README states it is in **public beta — "not recommended for production usage."**

A partially-built Antithesis harness already exists at `test/antithesis/` (jepsen-style serializability workload, `sk-recovery-race[-chaos]` clients targeting orioledb issue #855, an S3/minio setup variant, a health-checker). This research treats that harness as prior art: it encodes the team's own view of where the highest-value failure modes are, and several findings below extend or complicate what it already covers.

## 1. Architecture and Data Flow

*(Focus 1)*

- **In-process storage engine, no internal RPC on the hot path.** The tableam boundary is a plain C vtable, `orioledb_am_methods` (`src/tableam/handler.c:2441`). Almost all correctness bugs live in in-process concurrency (page-level locks, undo chains), not message loss.
- **Core Postgres is patched with OrioleDB-specific extension points**, confirmed in `/Users/artur/supabase/orioledb_postgres`: `get_xidless_commit_lsn_hook` (`xact.c:1404`), `snapshot_register_hook`/`snapshot_deregister_hook`/`reset_xmin_hook` (`snapmgr.c`, multiple sites), `xact_redo_hook` (`xact.c:6115,6269`), `CheckPoint_hook`/`after_checkpoint_cleanup_hook` (`xlog.c:7549,6140,7371`), `base_init_startup_hook`/`get_relation_info_hook`/`skip_tree_height_hook`/`database_size_hook`. OrioleDB's MVCC/undo state is kept consistent with core transaction/snapshot/checkpoint machinery via these hook call sites — any timing mismatch between a hook firing and OrioleDB's internal state update is structurally interesting for Antithesis.
- **Custom binary WAL protocol.** OrioleDB registers its own resource manager (`src/orioledb.c:396-409`, `rm_redo = orioledb_redo`, `rm_decode = orioledb_decode`) with packed record structs in `include/recovery/wal.h`, version-tagged by `ORIOLEDB_WAL_VERSION` (17, back-compat to 16). Three independent readers must agree on this format: crash recovery, logical decoding (`orioledb_decode`, `src/recovery/logical.c:1327`), and S3 archiving. Divergent interpretation between recovery and logical decoding is a serialization-boundary bug class specific to this rmgr.
- **Parallel WAL apply via shared-memory queues.** `src/recovery/recovery.c` distributes decoded WAL records to N recovery-worker background processes over `shm_mq` queues (`recovery.c:840,1130,1636`); each worker (`src/recovery/worker.c`) applies via `recovery_queue_process()`. Ordering/partitioning across queues and backpressure (`QUEUE_READ_USLEEP_*`, `worker.c:47-49`) is an internal RPC-like boundary that can break under injected scheduling delays or partial process kills mid-replay.
- **S3-backed storage mode: real network I/O boundary.** `s3worker` background workers (`src/s3/worker.c:119-132`) pull from a lock-free MPMC queue (`src/s3/queue.c`, `pg_atomic_uint64` + `ConditionVariable`s) and issue libcurl HTTP(S) calls with hand-rolled AWS SigV4 signing (`src/s3/requests.c:184-253`). `src/s3/archive.c` implements Postgres's `archive_module` interface over the same queue/worker machinery.
- **Checkpoint is two cooperating subsystems.** `src/checkpoint/checkpoint.c` (OrioleDB's own checkpoint: B-tree/undo state, sys-tree snapshots) is invoked *from inside* the core Postgres checkpointer via `CheckPoint_hook`. `src/checkpoint/control.c` maintains OrioleDB's own control file, separate from `pg_control`. Two independently-versioned control structures must stay consistent across crash.
- **Rewind: an in-database SQL-callable operation that can kill and respawn the whole Postgres process tree.** `src/rewind/rewind.c`: `orioledb_rewind_internal` terminates all other backends, performs the rewind, then either calls `try_restart_pg()` (`fork()` + `execl("pg_ctl restart")`) or sends `SIGTERM` to the postmaster. Gated by an OS-support check (disabled on Windows / no-`setsid` systems). Architecturally unusual and, per the Wildcard finding below, plausibly incompatible with the container process model used by the existing Antithesis harness.
- **Batched multi-row insert path** (`o_tbl_multi_insert`, `src/tableam/operations.c:563`) batches rows into one B-tree leaf under a single lwlock, with a self-documented tricky invariant: optimistic monotonicity check with a qsort fallback, and undo top-up capped at `2 * O_MAX_UNDO_RECORD_SIZE`.
- **Non-transactional catalog cache synced via syscache invalidation** (`src/catalog/o_sys_cache.c:425`) — a backend seeing a stale table descriptor would show up if invalidation delivery races with DDL commit + WAL.

## 2. State Management and Persistence

*(Focus 2, extended by Focus 6/Bug History and Focus 11/Unproven Assumptions)*

- **PK/SK checkpoint-boundary race (orioledb#855) — the fix exists, but has an acknowledged gap.** `ODBProcData.pendingSkUndoLoc` (`include/orioledb.h:267`) marks the PK-applied/SK-pending window; `checkpoint_write_pending_sk_fixups()` (`src/checkpoint/checkpoint.c:1004-1074`) emits a fixup WAL record for any backend caught in the window at checkpoint time, replayed on recovery via `apply_pending_sk_fixups()` (`src/recovery/recovery.c:342-675`). **The fixup record does not pin the referenced undo location against recycling** (`retainLocation = InvalidUndoLocation`, `checkpoint.c:1012`); `apply_one_pending_sk_fixup()` explicitly handles — and silently drops — the case where the undo record has already been recycled by replay time (`recovery.c:409-416`, comment: "recycled in the meantime; nothing we can do"). This is a plausible **surviving variant of #855** under a fault sequence that delays recovery replay or churns undo between checkpoint-write and replay (e.g., a lagging replica doing repeated restartpoints).
- **A second, distinct checkpoint-boundary crash-consistency bug: checkpoint abort-snapshot race.** `finish_write_xids()` (`checkpoint.c:902-948`) snapshots in-flight oxids purely via `oProcData[i].vxids[j].oxid` validity — it cannot know a backend's rollback WAL for that oxid has already been durably flushed below the checkpoint's replay-start boundary. A test (`test/t/replication_test.py::test_checkpoint_snapshot_resurrects_aborted_oxid`, added by commit `8a00a986`) deterministically reproduces: crash recovery re-discovers the oxid as in-flight, emits a spurious deferred `WAL_REC_ROLLBACK`, which — if a standby has already drained the resurrected oxid's undo-stack entry to 0 — causes `walk_undo_stack` to **PANIC the standby**. A consumer-side fix landed on `main` (commit `93db964d`, per a root-cause doc found on an unmerged branch `origin/add_stress_bank_account_test:test/t/crash/ISSUE_deferred_rollback_replica_two_crash_modes.md`); the doc explicitly notes an alternative primary-side fix (making the checkpoint's in-flight snapshot consistent with the replay-start boundary for aborts) was **not implemented** — only one of two failure legs was closed. Treat as a strong lead (test exists and is a real repro; primary-side gap is stated by the fix's own author, not independently re-derived here).
- **A third, currently-unresolved bug found in unmerged branch history (not on `main`): streaming-standby livelock.** Root-cause doc `origin/add_stress_test_pr:test/t/crash/ISSUE_streaming_standby_recovery_livelock.md`: eager per-backend WAL streaming can push in-flight modifications to a standby before commit/abort is decided; `recovery_finish` aborts in-flight oxids on the primary purely in memory with no WAL emitted; a streaming standby never runs `recovery_finish` itself, so the oxid can get stuck `INPROGRESS` forever, livelocking a later conflicting modify in `o_btree_modify_handle_conflicts`/`oxid_get_csn` (~1-in-6-to-11 repro rate per the doc). A fix (`fb1a8acc`/`714c99ca`/`9bc39d3b`, "Emit WAL_REC_ROLLBACK for in-flight oxids aborted by recovery_finish") was attempted **and reverted** (`3ea73f3d`, 2026-06-15) — **not present on `main`**. This is an open, unfixed lead per the team's own investigation notes, not a confirmed-fixed regression target.
- **CheckpointControl file** (`include/checkpoint/control.h:21-68`) is the single authoritative persistence-boundary record: `lastCheckpointNumber`, `lastCSN`, `lastXid`, `lastUndoLocation`, `toastConsistentPtr`, `replayStartPtr`, `sysTreesStartPtr`, retain-range fields, trailing CRC. `NUM_CHECKPOINTABLE_UNDO_LOGS = 2` (`control.h:28`) deliberately excludes `UndoLogRegularPageLevel` from checkpoint-time xid/undo bookkeeping — whether page-level undo has an independent consistency guarantee across checkpoint/crash is unconfirmed (open question).
- **Binary/on-disk versioning:** five independent version knobs (`ORIOLEDB_WAL_VERSION`, `ORIOLEDB_CHECKPOINT_CONTROL_VERSION`, `ORIOLEDB_BINARY_VERSION`, `ORIOLEDB_SYS_TREE_VERSION`/`ORIOLEDB_PAGE_VERSION`/`ORIOLEDB_COMPRESS_VERSION`), all one-way convertible except logical decoding (fails soft). `ORIOLEDB_BINARY_VERSION` mismatch is checked first; if it matches but a finer-grained constant was bumped without bumping the binary version, the finer check might never be consulted (untested lead).
- **S3 "decoupled storage" consistency model** (`doc/usage/decoupled-storage.mdx`, experimental): local disk is a write-back cache; S3 is authoritative only up to the last checkpoint. `s3_check_control()` (`src/s3/control.c:39-138`) enforces "local can be ahead of S3, never behind" at startup (behind → FATAL). Single-writer enforcement via conditional PUT lock file (`s3_put_lock_file()`, `control.c:143-278`, retries only on `CONDITION_CONFLICT`, FATALs on `CONDITION_FAILED` with a different lock identifier). Documented limitation: S3 history is retained forever, no GC mechanism.
- **Likely bug (Focus 8, static-analysis only, not runtime-verified): the S3 cross-instance lock file may be deleted on every ordinary backend/worker exit, not just final shutdown.** `orioledb_on_shmem_exit()` (`src/orioledb.c:1467-1474`) unconditionally calls `s3_delete_lock_file()` when S3 mode is set; it's registered via `before_shmem_exit` in `orioledb_shmem_startup()`, which runs once in the postmaster before fork and is thus inherited by every forked child (every client backend, checkpointer, bgwriter, s3worker). If true, **every ordinary client disconnect deletes the shared cross-instance S3 lock file**, defeating the single-writer guarantee. Flagged as a lead requiring runtime confirmation (open two connections, disconnect one, check whether `data/s3_lock` disappears while the instance is still up) before building a property on it.

## 3. Concurrency Model

*(Focus 3, extended with patched-Postgres findings)*

- Standard Postgres multi-process/shared-memory model, extended with OrioleDB-specific background workers (checkpointer-adjacent, bgwriter, S3 uploader, rewind worker, recovery workers) and page/undo-level locking layered on top of Postgres's own lock manager.
- **Stopevents mechanism** (`stopevents.txt`, `include/utils/stopevents_defs.h`, generated by `stopevents_gen.py`) is the team's existing deliberate race-injection tool — `pg_stopevent_set()` pins backends at named points. 35 stopevents currently defined, concentrated around checkpoint/undo/btree/recovery/split/scan. This is the same mechanism the existing `sk-recovery-race` driver uses (`sk_modify_pending` stopevent) and is a strong signal of which races the team already considers worth pinning deterministically.
- **Patched-Postgres concurrency surface (from `/Users/artur/supabase/orioledb_postgres`):**
  - **Checkpointer bootstraps deadlock-checker/relcache/catcache/sinval machinery it normally lacks** (`checkpointer.c:65-68,218-227`): stock Postgres's checkpointer never calls `InitDeadLockChecking()`/`RelationCacheInitialize()`/`InitCatalogCache()`/`SharedInvalBackendInit(false)`. OrioleDB's checkpoint process takes relation locks and fires stopevents, so this patch wires those subsystems in — a process whose original design assumption ("checkpointer doesn't take heavyweight locks") no longer holds. Combined with the documented checkpointer-vs-startup-process deadlock-avoidance code (`acquire_chkp_lock_drain`, `checkpoint.c:509-548`), this is flagged as the highest-value additional concurrency seam to fuzz beyond the already-covered PK/SK race: checkpoint + recovery + heavyweight locks all in one process.
  - `AcceptInvalidationMessagesHookType` (`inval.c:906-907`) — directly in the sinval/catcache concurrency path at transaction start.
  - `ReindexConcurrentlySkipHook` (`indexcmds.c:3570-3573`) — OrioleDB indexes opt out of Postgres's lock-heavy concurrent-reindex protocol.
  - No changes found in stock `lwlock.c`, `lock.c`, or `bufmgr.c` — the patch surface is narrow and hook-based, not a rewrite of core locking primitives.
- **Recovery worker parallel index build**: workers wait on `recovery_index_cv` for an index-build leader; no timeout observed in that wait path (open question — a stuck leader could stall other recovery workers indefinitely).

## 4. Claimed Safety Guarantees (leads to test, not verified facts)

*(Focus 4)*

- **SERIALIZABLE is not implemented via SSI**; `orioledb.serializable` GUC selects between `table_lock` (default, coarse `ExclusiveLock` per table for SERIALIZABLE txns), `error` (rejects SERIALIZABLE), and `repeatable_read` (silent downgrade, claimed equivalent to REPEATABLE READ since OrioleDB's CSN-based snapshot is already per-transaction stable) (`include/transam/oxid.h:106-171`).
- **Postgres "repeatable read" on OrioleDB tables is claimed to provide snapshot isolation**, explicitly called out in `test/antithesis/config/workload/jepsen-repeatable-read/compose.yaml` — this is the property the existing jepsen workload checks (no cycles/lost updates/aborted reads). Note: `test/antithesis/jepsen/Dockerfile`'s baked-in default env (`JEPSEN_ISOLATION=serializable`) conflicts with the workload config's override (`repeatable-read`/`snapshot-isolation`) — an unresolved naming/intent mismatch worth confirming with the team (no config actually exercises `orioledb.serializable=table_lock`/`error` mode today).
- **Row-level concurrency divergences from stock Postgres are explicitly documented as known/accepted, not bugs** (`doc/architecture/row-level-concurrency.mdx`): concurrent PK update errors out; a delete+reinsert-same-PK race can cause a concurrent updater to silently update the *new* row instead of erroring.
- **PK/secondary-key consistency after checkpoint+crash** is the claim already under direct test by `sk-recovery-race[-chaos]` (`always()` on PK-count == distinct-SK-token-count, plus `orioledb_tbl_check()` structural check; `reachable()` on the race window itself being reachable).
- **Recovery/replication idempotency for secondary indexes** (`doc/architecture/overview.mdx:147`, `doc/architecture/recovery.mdx:65`): "we cannot 'lose' any secondary index changes" during the toast-consistency window because secondary index trees are checkpointed later.
- **globalXmin monotonicity** is an explicit invariant (`src/recovery/recovery.c:2683-2691`), enforced only via `Assert()` — a no-op in non-assert builds, relevant since violations may go unnoticed outside debug/assert-enabled Antithesis images.
- **Copy-on-write checkpoint consistency**: "a consistent tree image exists in storage every moment" (`doc/architecture/overview.mdx:77`).
- **Cross-worker replay-visibility ordering**: a transaction is visible to readers only once *all* recovery workers have completed all associated work (`doc/architecture/overview.mdx:153`).
- **Page checksums are computed and compared, but a mismatch only WARNs, not ERRORs** (`src/btree/io.c:1310-1328`, explicit `TODO: maybe ereport(ERROR) here once caller cleanup is safe`). A tension worth testing directly: does a corrupted page ever get silently used after only a WARNING?
- **S3 mode single-writer / durability claims** (`doc/usage/decoupled-storage.mdx`): re-attaching an empty instance to the same bucket recovers all data as of the last checkpoint; only one instance may hold a bucket at a time (see the likely lock-file-deletion bug in §2 that may undermine this).
- **Rewind claims its own limitations explicitly** (`doc/usage/rewind.mdx`): not safe across a crash/interruption during the rewind phase itself ("the database may be left in an inconsistent state") — a self-disclaimed guarantee, i.e. crash-during-rewind is *not* claimed safe, making it a legitimate (not gratuitous) Antithesis target.
- **Binary compatibility non-guarantee**: cross-architecture data-directory portability is explicitly *not* promised (`doc/contributing/binary-compatibility.mdx:25-29`), even across machines with matching endianness/alignment/float format.

## 5. Claimed Liveness Guarantees (leads to test, not verified facts)

*(Focus 5)*

- **Rewind worker undo-space reclamation is conditional, not unconditional**: doc explicitly says space grows indefinitely "if the worker lags" and can block VACUUM if stuck on an old transaction (`doc/usage/rewind.mdx:36-45`).
- **Rewind operation has bounded abort timeouts** (100s for worker stop, 100s for backend stop, `src/rewind/rewind.c:837-872`) but automatic restart-after-rewind is explicitly a **single best-effort attempt, not retried** (`doc/usage/rewind.mdx:99-101`).
- **Checkpointer-vs-recovery lock drain** (`acquire_chkp_lock_drain`, `checkpoint.c:509-548`) claims eventual forward progress ("worst case is a few extra iterations").
- **S3 queue erased-location advancement** is claimed always guaranteed (`src/s3/queue.c:315-322`), and S3 data is recoverable "in the state of the last checkpoint" (`doc/usage/decoupled-storage.mdx`).
- **Recovery worker replay lag**: a known ~10-second lag exists and is proactively mitigated by waking the startup process immediately (`src/recovery/worker.c:746-756`) rather than waiting for the normal poll interval.
- **bgwriter undo-location advancement for replica cleanup has a single named point of responsibility** (`BGWriterNum == 0`, `src/workers/bgwriter.c:200-214`) — if that specific worker stalls, crashes, or is disabled (`orioledb.debug_disable_bgwriter`), the claimed replica-cleanup liveness may not hold.
- **The existing Antithesis harness already operationalizes one liveness property**: `sk-recovery-race-chaos/driver.py` asserts via `sometimes()` that at least one automatic checkpoint fires under concurrent DML load (backed by `checkpoint_timeout=30s`).
- **Gaps (liveness expected but not documented):** no GC for S3-resident historical data (documented absence); no stated bound on checkpoint termination under arbitrary concurrent split/merge load; no stated bound on S3 uploader catch-up time or backpressure/failure semantics under sustained write pressure or prolonged S3 unavailability; the Antithesis health-checker (`test/antithesis/health-checker/main.go`) only checks `pg_isready`, not that OrioleDB's own recovery/undo state has finished catching up — a readiness-gate blind spot.

## 6. Failure and Degradation Modes

*(Focus 8)*

- **S3 request layer has essentially no timeouts and no retries.** `src/s3/requests.c` never sets `CURLOPT_TIMEOUT`/`CURLOPT_CONNECTTIMEOUT`; a stalled-but-alive connection can block indefinitely. Any non-whitelisted error escalates straight to `ereport(FATAL, ERRCODE_CONNECTION_EXCEPTION)` (`requests.c:247,350,582`) with no retry loop.
- **S3 worker "retries" only by crash-looping.** `register_s3worker()` sets `bgw_restart_time = 0`; a FATAL kills the worker, which is respawned immediately and re-executes the same task from shared-memory state. Verified against patched-Postgres (`postmaster.c:2691-2711`) that exit status 1 does not trigger a full-cluster restart — but if the bucket is genuinely unreachable, the crash-loop never terminates.
- **Checkpoint blocks forever, uninterruptibly, if S3 is down.** `s3_workers_wait_for_flush()` (`src/s3/worker.c:139-163`) polls with no `CHECK_FOR_INTERRUPTS()` and no timeout, called from every checkpoint's tail (`s3_workers_checkpoint_finish()`). Combined with the crash-loop above: **any checkpoint hangs indefinitely and uncancellably once S3 becomes unreachable.**
- **Page-part load/lock busy-waits have no timeout and no interrupt checks** (`src/s3/headers.c:671-748`, `while (status == Loading || status == Evicting) pg_usleep(10000L)`), contrasted with `acquire_chkp_lock_drain()` in the checkpoint code, which does the "right" pattern (`pg_usleep` + `CHECK_FOR_INTERRUPTS()`) — showing the codebase knows the correct idiom but doesn't apply it consistently to the S3 path. Same shape recurs in `wait_finish_active_commits()` and the SK-fixup wait loop.
- **Startup-time S3 lock-file handshake is single-shot FATAL, not retried** for any failure other than the specific `CONDITION_CONFLICT` case — a transient S3 blip at exactly instance-startup time prevents the whole instance from coming up.
- **Unbounded wait for the WAL archiver inside a checkpoint (S3 mode)** (`checkpoint.c:1925-1934`, `while (!check_archive_done(...)) pg_usleep(100000L)`), no timeout/abort — since checkpoints gate clean shutdown, a persistently-failing archiver could make the instance unable to shut down cleanly.
- **A "new" livelock possibly introduced by the #855 fix itself:** for self-created tables (the `WaitingSkUndoLoc` sentinel fast path), `checkpoint_write_pending_sk_fixups()` spins unboundedly with no `CHECK_FOR_INTERRUPTS()` (`checkpoint.c:1023-1041`) waiting for the backend to clear the sentinel — worth checking this isn't just relocating the original race rather than closing it.
- **Retry-with-backoff patterns exist elsewhere** (`src/recovery/worker.c:703-785` exponential backoff on queue reads; `o_indices.c:1576`/`o_tables.c:1459` capped exponential backoff for catalog deserialization races) — sharpening the point that the S3 paths conspicuously lack the idiom the codebase otherwise knows how to apply.
- The Antithesis health-checker (`main.go`) writes a static "setup complete" marker unconditionally on process start — it never probes whether Postgres can actually serve a query, mirroring exactly the "health check says healthy but can't serve" pattern this focus looks for.

## 7. External Dependencies and Integration Points

*(Focus 9)*

- **Patched PostgreSQL core is a build/ABI dependency**, not a runtime "down/degraded" one — vanilla Postgres cannot load the extension (`orioledb.c:1565`, custom rmgr registration). Confirmed orioledb-specific core patches (beyond the concurrency-focused ones in §3): `xact_redo_hook`, a "recovery target reached" hook, `database_size` hook, `tuple_complete_modification` TableAM callback, `verify_tableam` (amcheck support), replication-origin advance for xid-less commits. Binary/version drift is guarded by the version constants in §2; no Antithesis coverage targets a Postgres-patch/orioledb version mismatch directly (it would surface as a build failure, not a simulation finding).
- **S3-compatible object storage**: hand-rolled AWS SigV4 signing over libcurl + OpenSSL, no AWS SDK. As in §6, no explicit timeouts/retries. SigV4 signing depends on wall-clock time (`time(NULL)`/`gettimeofday`) — an implicit NTP/clock-sync dependency between the orioledb host and the S3 endpoint; clock skew would manifest as auth failures indistinguishable from misconfiguration. `orioledb.s3_desired_size` local-eviction "requires a filesystem that supports sparse files" (documented).
- **No fallback/degradation path exists for S3 mode** — if S3 is unavailable at startup or checkpoint time, the affected process FATALs rather than degrading to local-only operation.
- **Existing antithesis S3 setup config has no deliberate minio fault injection wired in** (`test/antithesis/config/setup/s3/env` is empty) — any minio unavailability during a run would come only from Antithesis's generic container-fault injection, not a targeted assertion.
- **Container topology / DNS**: Docker Compose's internal DNS + `depends_on: condition: service_healthy` gates startup ordering in the existing harness — an implicit dependency on Compose's healthcheck polling, not customer-facing but relevant to how the harness itself could mask or race with real failures.

## 8. Bug History and Density

*(Focus 6 — grep-based density signals, not exact counts; git log searches scoped to this repo, plus primary-evidence root-cause docs found on two unmerged remote branches)*

- **Hottest files by commit count**: `src/recovery/recovery.c` (159 commits, single hottest file), `src/checkpoint/checkpoint.c` (117), `src/transam/undo.c` (112), `src/transam/oxid.c` (67). Recurring themes: recovery-leader/worker xmin & undo-stack bookkeeping, checkpoint-vs-concurrent-commit/abort races, undo-stack location tracking and CSN visibility regimes.
- **A striking revert cluster**: of the last ~28 revert-titled commits, a large majority touch recovery/checkpoint/undo/xmin/commit-flow — the most-churned, most-reverted area in the whole history, consistent with genuinely hard concurrency problems rather than simple mistakes.
- **The consistency checker itself has had correctness problems**: "Don't misreport phase-1 splits as leaked extents in `orioledb_tbl_check`" was implemented and reverted twice; "Suppress BROKEN_SPLIT NOTICE" and "phantom-leak expectations" fixes recur. Because `orioledb_tbl_check()` is the oracle the existing `sk-recovery-race` harness uses to assert consistency, its own historical instability is worth validating before leaning on it further as an Antithesis oracle.
- **Three primary-evidence bug narratives found (root-cause docs on unmerged branches `origin/add_stress_bank_account_test` and `origin/add_stress_test_pr`, read via `git show`)**: the checkpoint abort-snapshot race (fixed on `main`, one of two failure legs closed — §2), the streaming-standby livelock (root-caused, reproduced by the team, **not fixed on `main`** — §2), and the already-tracked #855 PK/SK race (fixed, target of the existing harness). Several other issue-doc filenames on those branches were **not** read in depth this pass (`ISSUE_TOKEN_LEAK_COMMIT_ASSERT.md`, `ISSUE_TOKEN_LEAK_PRE_COMMIT_WAL_FINISH.md`, `ISSUE_recovery_committed_oxid_reverts_to_inprogress.md`, `extent_leak_issue.md`, `sk_leak_issue.md`, a `livelock_investigation/` subfolder) — flagged as an open follow-up area, likely containing at least two more distinct leak bugs and a "committed oxid reverts to in-progress" bug.
- **Quiet-but-complex areas** (low fix density relative to apparent complexity): `src/workers/` (bgwriter/interrupt, only 22 commits across 4+ years despite mediating undo-eviction concurrency); `src/rewind/` (only 22 commits, but see the Wildcard finding below — likely reflects youth, not safety, and has its own dense recent bug history when measured by file rather than directory); `src/s3/` (87 commits, proportionally lower fix density than core recovery/undo despite overlapping concurrency surface).
- **Correction to the directory-level "quiet" read for rewind**: the Wildcard pass found `src/rewind/rewind.c` + `include/rewind/` specifically has **164 commits** with a dense recent defect history (buffer/overflow fixes, checkpoint-vs-eviction races, reader bugs, an assert-in-production fix, and a commit literally titled "Debug rewind crash") — reconciling the two passes: the *directory* commit count is unremarkable, but the *feature*, once isolated, is actually one of the most actively-churned and defect-dense in the tree.

## 9. Existing Test Strategy

*(Focus 7)*

| Category | Location | What it covers | What it doesn't |
|---|---|---|---|
| SQL regression | `test/sql/*.sql` + `test/expected/*.out` (49 files), `make regresscheck` | DDL/DML correctness, planner, types, compression, TOAST | No concurrency, no faults |
| Isolation tests | `test/specs/*.spec` (32 files), `make isolationcheck` | Multi-session interleaved locking/MVCC/deadlock (10 use stopevents) | Single-process scheduler only; no OS/process-level faults |
| Python/testgres integration | `test/t/*_test.py` (68 files), `make testgrescheck` | Crash/recovery (stopevent + `SIGKILL`), replication (`replication_test.py`, 43 methods, largest file), S3 (mocked via `moto`), eviction, backup, logical replication, amcheck | S3 tests use a mocked/in-process fake — no real network latency/partition/timeout; deterministic scripted `SIGKILL` only, not randomized fault timing |
| Backup tool integration | `test/integration/` (pgbackrest, wal-g) | Real backup tools, PITR | Not wired into CI/`installcheck`; no fault injection during backup/restore |
| CI matrix | `.github/workflows/check.yml` | gcc/clang × PG16/17 × normal/debug/sanitize/valgrind/check_page/static | Valgrind incidentally perturbs timing (closest thing to chaos pre-Antithesis) but still fully deterministic, single-machine |
| **Antithesis harness** | `test/antithesis/` | jepsen serializability/upsert-anomaly workload; `sk-recovery-race`/`sk-recovery-race-chaos` (orioledb#855); S3/minio setup variant; health-checker | `flake1` is TODO; no replication topology; no real S3 fault injection wired to an assertion |

**Key overlap**: `sk-recovery-race` directly mirrors `test/t/recovery_test.py::test_recovery_sk_modify_pending_concurrent` (same stopevent, same 3-way DML race, same checkpoint trigger) — Antithesis's value-add there is specifically *other* faults landing in the same window (disk stall, scheduling delay), not rediscovering the crash-consistency issue itself.

**Key gaps** (not covered anywhere, and not duplicated by existing Antithesis work):
1. **No primary/standby replication scenario under fault injection anywhere** — `replication_test.py`'s ~43 deterministic methods have no Antithesis analogue; the Antithesis base topology has no second Postgres node. Given §2/§8's findings (checkpoint abort-snapshot race requires a replica to PANIC; the streaming-standby livelock is unfixed on `main`), this is the single largest and highest-value coverage gap.
2. **Real S3/network fault injection** — existing S3 tests use `moto` (mocked); the Antithesis `setup/s3` minio container is real but has no fault-injection workload targeting it yet.
3. **Infrastructure-level faults** (OOM-killer, disk-slow-not-dead, CPU starvation, network partition, clock skew) — none exercised by the deterministic suites; this is squarely Antithesis's unique value.
4. **Backup/restore under fault injection**, **logical replication/decoding under faults** — no Antithesis counterpart to either.
5. **Rewind feature** — zero stopevents, zero Antithesis config exposure (`orioledb.enable_rewind` never set in any harness config) despite being one of the most defect-dense subsystems (see §8, §11).

## 10. Product Context

*(Focus 10)*

Ranked user workflows by doc emphasis and failure severity:

1. **Normal CRUD/OLTP traffic** — highest impact: wrong query results or lost writes (serializability anomalies) is the worst-case failure for a database engine, and is exactly what the existing jepsen workload already targets.
2. **Checkpoint/crash recovery/replication** — highest impact: PK/secondary-index divergence after crash is silent, hard-to-detect corruption surfacing only on index-scan queries; already the single most concretely-tracked bug class (#855) and the origin of the existing `sk-recovery-race[-chaos]` harness.
3. **Backup/restore and disaster recovery** — medium-high impact, concentrated at incident-response time. `pg_rewind` explicitly documented as *not* incrementally supported for OrioleDB tables (copies them completely). `orioledb.replay_until_lsn` is flagged in docs as a "last-resort" mechanism that "intentionally induces a split-brain state" between heap and orioledb tables.
4. **Rewind ("oops" recovery)** — high impact when triggered (the feature's entire purpose is data safety, so a rewind that corrupts instead of restores is the worst possible failure for it), but low usage frequency (experimental, off by default). Docs pre-confess a crash-during-rewind inconsistency risk.
5. **S3-backed decoupled storage / compute-storage scaling** — high severity if it fails (dual-writer corruption, unrecoverable bucket state) but currently opt-in/experimental. Primary+replica each need separate buckets (documented limitation — replication + S3 not really supported together yet).
6. **Compression/fillfactor/tuning, non-btree "bridge" indexes** — low-medium impact, mostly perf; compressed-tree free-space management is called out as needing "more complex mechanisms" (two system trees) — a plausible corruption vector under concurrent compaction+crash.
7. **Integrity verification (`verify_orioledb()`/`pg_amcheck`)** — itself a user workflow; takes only `AccessShareLock` and is claimed not to block concurrent traffic nor false-fail during a concurrent checkpoint — a concurrency-correctness claim worth testing directly (see §8's note on the checker's own historical instability).

Open question: whether any of this is exposed in a Supabase-hosted product today, or is purely upstream-project framing (affects how much "managed-service user" severity framing should weigh in prioritization).

## 11. Unproven Assumptions

*(Focus 11, cross-referenced with Focus 12/Wildcard)*

- **§6's S3-always-reachable assumption has a crash-amplifying consequence**: an `ereport(FATAL)` in a shmem-attached backend/bgworker is treated by the postmaster as an abnormal exit, which (per standard Postgres `HandleChildCrash` behavior — not independently verified live in this patched tree) triggers a cluster-wide crash-restart: every other backend killed, shared memory reinitialized, WAL replayed. A transient S3 blip during a checkpoint upload or on-demand page-part load could disproportionately escalate into a full-instance crash-restart, and if sustained, a crash-restart loop.
- **S3 header/part-lock spin-waits assume the loader always eventually flips status back** (`headers.c:690-748`) — currently only reachable-but-masked because the FATAL above resets shared state via crash-restart; if S3 failure handling is ever made non-fatal without also adding a timeout here, this becomes a genuine livelock.
- **Checkpoint-during-recovery LSN capture is explicitly marked unsynchronized with parallel recovery workers**: `get_checkpoint_xlog_ptr()` (`checkpoint.c:1322-1332`) has a `/* FIXME: synchronize recovery workers */` comment and returns the leader's own replay pointer as a stand-in for "what all workers have applied." This LSN feeds `toastConsistentPtr`, which is exactly the boundary `checkpoint_write_pending_sk_fixups()` (the #855 fix) uses. Contrast: `finish_write_xids()`, called later in the same checkpoint function, *does* properly wait for every parallel recovery worker to catch up — the earlier LSN capture has no equivalent synchronization. Confirmed reachable: `CheckPoint_hook` fires from `CreateCheckPoint()`, including `CHECKPOINT_END_OF_RECOVERY`, which runs while `RecoveryInProgress()` is still true and parallel recovery workers are active — **this is the same assumption class that #855 violated, relocated from the live-DML path to the recovery/promotion path**, and not covered by the existing `sk-recovery-race` harness (which targets live DML, not end-of-recovery checkpoints).
- **Unbounded wait for the WAL archiver inside a checkpoint (S3 mode)** (`checkpoint.c:1925-1934`) assumes the archiver always eventually succeeds — no timeout/abort path.
- **A possibly-new livelock introduced by the #855 fix's own self-created-table fast path** (`checkpoint.c:1023-1041`, the `WaitingSkUndoLoc` sentinel spin) assumes the backend that set the sentinel always finishes promptly; no bound, no interrupt check, explicitly justified only against deadlock, not against liveness under scheduling faults.
- Lower-priority leads: an author-acknowledged race in `MOVE DATABASE`-style tablespace moves under hot standby (`recovery.c:4019`, "XXX there is a race condition here"); a lock-manager-shaped `elog(PANIC, "failed to re-find shared proclock object")` (`oxid.c:1262`); an undo-buffer wraparound retry guarded by "this situation shouldn't happen twice" (`undo.c:2076`); a `CHECK_PAGE_STRUCT`-only structural corruption trip-wire (`page_state.c:851`, `elog(PANIC, "broken page")`) — worth keeping enabled in Antithesis builds so races surface as attributable failures rather than silent corruption.

## 12. Wildcard / Cross-Cutting Findings

*(Focus 12)*

- **Headline finding: the "rewind" subsystem is large, actively-churned (164 commits), and has zero Antithesis exposure, with a plausible container-fatal interaction not covered by any other focus.** No stopevent exists for any rewind code path (unlike PK/SK, it can't be pinned deterministically — only chaos-style probing is possible). `orioledb.enable_rewind` defaults off and is never set in any `test/antithesis/config/**` file.
- **Concrete container-topology hypothesis (reasoned from code + Docker/tini semantics, not yet empirically verified — flagged explicitly as unconfirmed):** `docker/init/docker-entrypoint.sh` ends in `exec "$@"`, making `postgres` (the postmaster) the direct child that Docker Compose's `init: true` (tini) watches. Tini exits once *that specific direct child* exits, regardless of grandchildren. `try_restart_pg()`'s forked grandchild execs `pg_ctl restart`, which stops the *original* postmaster before starting a new one — but the original postmaster exiting is exactly the event that makes tini (PID 1) exit too, plausibly tearing the whole container down before/concurrently with the new postmaster coming up as an orphaned descendant. Base compose config uses `restart: on-failure:2` (shared budget with any other fault-injected crash); the two `sk-recovery-race*` workload configs override to `restart: always`, but a future workload enabling rewind on the default/jepsen config would inherit the 2-attempt cap. If exhausted, this produces a silent, permanent outage the health-checker would report as an infra failure rather than a specific property violation — a **false signal that would be confusing to triage** if this happens during a run investigating something else. Needs empirical validation (a real `make up` + `SELECT orioledb_rewind_to_timestamp(..., true)` run) before being treated as fact; also unconfirmed whether Supabase's actual production deployment runs postgres as container PID 1 at all (this may be an Antithesis-harness-specific artifact rather than a real deployment risk).
- `orioledb.replay_until_lsn` (a second, smaller "controlled recovery cutoff" GUC) has the same pattern — unused anywhere in `test/antithesis/`, lower priority than rewind.
- Minor inconsistency: `setup/s3/compose.yaml` uses uncapped `restart: on-failure` while base/sk-recovery-race configs use different capped/always policies — worth normalizing if S3 mode is ever combined with a workload that relies on the restart policy for fault recovery.

## Assumptions and Open Questions

- Several findings above (S3 lock-file deletion on every backend exit; the checkpoint-during-recovery LSN synchronization gap; the FATAL→cluster-crash-restart escalation path; the rewind/tini container interaction) are **static-analysis leads, not runtime-confirmed defects**. Each should be empirically validated (per `references/validating-claims.md`) before a property assertion is built that assumes the defect is real, per the individual agent's own stated caveats above.
- The checkpoint abort-snapshot race and the streaming-standby livelock were found via root-cause docs on **unmerged remote branches** (`origin/add_stress_bank_account_test`, `origin/add_stress_test_pr`) not present in this branch's worktree — read via `git show <ref>:<path>`. Only 2 of roughly 8-10 issue docs on those branches were read in depth; several filenames suggest additional undiscussed bugs (token-leak, extent-leak, "committed oxid reverts to in-progress") that a follow-up pass should read in full.
- Whether `Assert()`-only invariants (e.g., globalXmin monotonicity) are compiled into the images actually used for Antithesis runs is unconfirmed — assert-enabled builds would turn violations into crashes Antithesis can catch; release builds would silently continue. This should be confirmed before relying on any `Assert()`-backed invariant as an Antithesis signal.
- Whether Antithesis's generic container-fault injection actually reaches the `minio` container in `setup/s3` runs (vs. only workload client containers) is inferred, not empirically verified.
- Whether any of this system is exposed in a Supabase-hosted product today is unconfirmed — affects how much weight "managed-service user impact" framing should carry.
- Page-level undo (`UndoLogRegularPageLevel`)'s checkpoint/crash consistency guarantee (or lack thereof) was not traced to a conclusion — it's excluded from `NUM_CHECKPOINTABLE_UNDO_LOGS` bookkeeping, but whether it has an independent guarantee is open.
