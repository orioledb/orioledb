# readiness-gate-standby-recovery-lag

## STATUS: corrects/narrows a sut-analysis lead based on firsthand code tracing

sut-analysis §5 states: "the Antithesis health-checker (`test/antithesis/health-checker/main.go`) only checks `pg_isready`, not that OrioleDB's own recovery/undo state has finished catching up — a readiness-gate blind spot." The task asked this research pass to pay particular attention to this claim. Having traced the actual synchronization code (not done in the original pass), **the claim does not hold for the scenario the current harness actually exercises** (single-node crash recovery). It does plausibly hold for a scenario the harness doesn't have yet (a hot/warm standby). This file records both the correction and the narrower, still-real property.

## What was checked

1. **The health-checker itself is even weaker than described, but harmlessly so.** Reading `test/antithesis/health-checker/main.go` in full: it does not call `pg_isready` or touch the database at all — it's a static Go binary that unconditionally writes the Antithesis `setup complete` marker JSON the instant it runs, with zero I/O to Postgres. The *actual* `pg_isready` check lives one layer up, as the Compose `healthcheck:` stanza on the `orioledb` service itself (`test/antithesis/config/docker-compose.base.yaml:20-36`), which gates the `health-checker` container's own startup via `depends_on: condition: service_healthy` (`docker-compose.base.yaml:43-45`), and in turn gates the workload-client containers the same way. So the readiness signal really is `pg_isready`-only, just implemented one level of indirection away from where sut-analysis's text implies.

2. **For a single-node crash-recovery-then-ready transition (the only topology the current harness has, per sut-analysis §9 gap #1), `pg_isready` structurally cannot succeed before orioledb's own recovery workers have drained.** Traced the full call chain in the patched Postgres source (`/Users/artur/supabase/orioledb_postgres`):
   - `xlogrecovery.c:1901` calls `RmgrCleanup()` (a stock-Postgres function, `src/backend/access/transam/rmgr.c:74-84`) synchronously inside `PerformWalRecovery()`, which runs as part of `StartupXLOG()`, which the startup process runs to completion **before** the postmaster ever logs "database system is ready to accept connections" (`postmaster.c:2448`) or begins accepting client connections.
   - `RmgrCleanup()` calls every registered resource manager's `rm_cleanup` callback. OrioleDB's rmgr registers `rm_cleanup = o_recovery_cleanup` (`src/orioledb.c`), which calls `o_recovery_finish_hook(true)` (`src/recovery/recovery.c:1261`).
   - `o_recovery_finish_hook()` calls `workers_send_finish(false)` then, for every recovery worker, `worker_wait_shutdown(&workers_pool[i])` (`recovery.c:1275`). Reading `worker_wait_shutdown()`'s body directly: it's an unconditional `while (true) { CHECK_FOR_INTERRUPTS(); ...; if (status == BGWH_STOPPED) break; pg_usleep(200); }` loop — **no timeout, no escape hatch** other than the worker actually stopping (or the postmaster dying).
   - Therefore: the startup process cannot finish `StartupXLOG()` until every orioledb recovery worker has fully drained its queue and stopped — and the postmaster cannot open for connections (and `pg_isready` cannot succeed) until `StartupXLOG()` finishes.

   **This directly refutes the literal "crash recovery just finished but pg_isready says ready anyway" framing** for the topology the harness currently has.

## Why the underlying concern is still real, just mis-scoped

The mechanism above only applies because, in the current harness, "the instance becomes ready" and "recovery finishes" are the *same* lifecycle event on a single node. That symmetry breaks the moment a **hot/warm standby** is introduced (a currently-missing topology — sut-analysis §9 flags "no primary/standby replication scenario under fault injection anywhere" as the single largest coverage gap). On a streaming standby with `hot_standby = on`, Postgres by design accepts read-only connections **while recovery is still continuously ongoing** — that's the entire point of hot standby, and `pg_isready` succeeds as soon as the standby starts accepting those connections, long before "recovery is caught up" has any meaning (it never fully "finishes" on a standby that's still streaming). sut-analysis's own §5 also separately notes "Recovery worker replay lag: a known ~10-second lag exists," sourced from a comment in `src/recovery/worker.c:746-756` — but that comment is specifically about `pg_stat_replication` feedback timing for synchronous-replication purposes, not about `pg_isready`/connection-acceptance readiness; it's a related-but-distinct liveness detail, not itself evidence for the readiness-gate gap.

So: the real, still-standing version of this property is **"on a streaming standby, is there any externally-observable signal that safely distinguishes 'caught up enough for fault injection to target interesting state' from 'still far behind,' or does the harness's `pg_isready`-based gate treat both identically?"** — and it cannot be tested at all until a standby node exists in the harness.

## Why this matters

If/when a replica topology is added (as sut-analysis §9 recommends as the top-priority coverage gap), reusing the existing `pg_isready`-based `depends_on: condition: service_healthy` pattern for the standby's readiness would silently carry this gap into the new topology — a workload or Antithesis-driven fault could begin targeting the standby (e.g., promoting it, or reading from it) while it is arbitrarily far behind, without any way to distinguish that from a caught-up standby, unless a different readiness probe is used for that node specifically.

## Antithesis SDK angle

- **Type recommendation:** Reachability / Safety, but explicitly **conditional on future harness work** — this cannot be implemented as a property against the current single-primary topology, since there's no standby to observe. Recorded now so that whoever builds a replication-topology workload (sut-analysis §9's top gap) inherits this finding rather than rediscovering it, and so the natural instinct to reuse the existing `pg_isready` healthcheck pattern for a new standby service is caught at design time.
- **Corrected primary-node property (still worth keeping, smaller in scope):** `Always()` — for the single-primary topology, confirm (as a positive regression check, not a suspected-bug hunt) that a client connection succeeding via `pg_isready` implies `orioledb_get_current_oxid()`/recovery-status functions report "not in recovery," protecting the synchronization chain traced above against a future refactor accidentally breaking it (e.g., someone adding a timeout to `worker_wait_shutdown()` for unrelated reasons and inadvertently reintroducing the gap this file just spent effort ruling out).

## Investigation Log

### Does OrioleDB's recovery-worker-drain step really happen before Postgres opens for connections?

- Examined: `src/recovery/recovery.c` (`o_recovery_finish_hook`, `worker_wait_shutdown`), `src/orioledb.c` (rmgr registration), and `/Users/artur/supabase/orioledb_postgres/src/backend/access/transam/{rmgr.c,xlogrecovery.c}` and `postmaster.c` (for `RmgrCleanup()`'s call site and the "ready to accept connections" log line's position).
- Found: `RmgrCleanup()` is called once, synchronously, inside `PerformWalRecovery()` (`xlogrecovery.c:1901`), and this entire function runs to completion inside `StartupXLOG()`, which is called by the startup process before the postmaster can transition to accepting connections. `worker_wait_shutdown()` has no timeout. This chain is solid.
- Not found: did not perform a live test (no `make up` + kill -9 + observe `pg_isready` timing performed); this is a static-code trace, albeit an unusually thorough one for this batch of properties, since the whole point was to check whether the sut-analysis lead survived scrutiny.
- Conclusion: the specific "crash recovery on the primary just finished but pg_isready declares ready anyway" framing from sut-analysis §5 is refuted for the current single-node topology by this trace. The underlying class of concern (readiness gate insufficiency) is redirected to the hot-standby scenario, which is real but currently untestable (no standby exists in the harness).
